# 決定事項と実装時の判断

更新: 2026-11-06。機能仕様の正本は [確定仕様](next-app-spec.md)。この文書は過去の会話を読む代わりに、決定の理由を伝えるもの。

## ユーザーが決めた方向性

| 決定 | 理由・背景 |
| --- | --- |
| 新規のElectron・TypeScript・Reactアプリ | 旧アプリの見た目と操作感、入力項目の多さがコンセプトから離れたため |
| Notionを参考にしたシンプルなページ・表 | 装飾より情報への到達と入力の軽さを重視 |
| 共通の検討項目ページ | 実験も作業も気づきも、別々の仕組みに分ける必要がない |
| 気づきは独立ページ | 別の実験で確かめることを、後から一覧で振り返りたい |
| 共通の状態選択 | 気づき由来の項目だけ「次へ」の専用操作を持つと分かりにくいため |
| 状態は6種類 | 未着手・進行中・待ち・完了・中止・いつか。旧候補の「あとで」「次にやる」「保留」は使用しない |
| ホームは表形式の主一覧 | 今相手にする項目を検索・フィルター・並べ替えで確認したい |
| いつか欄はホームに常設 | 独立ページだと見なくなるため。主一覧には混ぜない |
| 完了・中止はホームから除外 | 記録は保持し、テーマや検索から参照・再開する |
| 実施条件をサマリへ一般化 | 状態を問わず、実施条件・現在の状況・メモを短く書けるようにする |
| 所属テーマは1つ | 検討項目が複数テーマをまたぐ運用はしない。未所属は可能 |
| 資料は文脈と目録の両方から | 実験のマニュアル・手順書・実験メモ・計算シートをまとめ、全資料の一覧からも探したい |
| 本文に画像を追加 | 視認性を上げる。画像によるサムネイル一覧は将来候補 |
| ガントは独立した計画 | 全検討項目への開始・終了日入力は煩雑なため |
| 当初予定と実績の比較 | 報告に便利だが管理負担がある。実装して使用感を確認する |
| PowerPointへ画像コピー | 進捗報告で計画を貼り付けて提示するため |
| 期限と確認日を両方用意 | 完了させたい日と、将来の検討を見直す日を区別する |
| 分類・資料セットは見送り | 初期版の入力と整理を増やさず、必要になってから追加する |
| 旧データ移行なし | 移行対象の実データは存在しない |

## 実装上の既定方針

SQLite、main/preload/rendererの分離、自動保存と復旧下書き、本文画像の管理保存、DBと添付のバックアップ、30分周期・30世代保持は、確定仕様で採用した設計上の既定方針。ユーザーの追加操作や新しい必須プロパティを増やさない。

画像形式・上限、サマリ長、ライブラリとバージョン、詳細なスキーマ、配布方式、検索性能基準、列幅やスクロール構成はPhase 0以降に理由を記録して決める。これらが未指定でも開発は開始できる。

## 試作と製品で区別すること

- 試作はやりたいことと情報構造の確認用。縦の長さや余白は承認済みの完成デザインではない。
- 当初予定の保存・実績日入力・画像プレビューは試作で操作確認したが、実機運用の負担は今後確認する。
- 原本起動・DB・画像添付・バックアップ・Windowsの画像コピーは製品として未検証。
- 試作の複数テーマ資料管理は1テーマのサンプルに簡略化されている。製品では同一資料を複数テーマ・複数項目から参照できる。

## Phase 0の境界と配置

- mainがウィンドウと保存領域を管理。preloadはメソッド単位のAPIを公開する。rendererにDB、fs、任意パス／任意チャンネル／任意コマンドの入口を設けない。現在のAPIは引数なしの `getAppInfo(): Promise<AppInfo>` のみ。
- mainでは送信元WebContents・メインフレーム・読込URLの一致、引数が空であることを検証する。今後の書込APIもmainで実行時検証し、失敗を型付き結果で返す。
- `nodeIntegration: false`、`contextIsolation: true`、`sandbox: true`。preloadは実行時にもsandboxed/contextIsolatedを要求する。[Electronセキュリティ](https://www.electronjs.org/docs/latest/tutorial/security)、[sandbox](https://www.electronjs.org/docs/latest/tutorial/sandbox) に沿い、別ウィンドウ・任意ナビゲーション・webview・権限要求を拒否する。
- 製品画面はローカルのビルド済みHTMLのみ。CSPはselfを基本にし、unsafe-evalを許可しない。開発時だけ127.0.0.1:5173を使用し、React Refreshのインライン初期化を許可する。製品ビルドにその許可は含めない。
- 保存先は `%LOCALAPPDATA%/EngineeringWorkspace/{development|production}/`。Windowsの非ローミング領域を使い、プロジェクト／OneDrive／旧アプリの保存先へDBを置かない。[Windowsの既知フォルダー](https://learn.microsoft.com/en-us/windows/win32/shell/knownfolderid)、[app.setPath](https://www.electronjs.org/docs/latest/api/app) を参照。フォルダ改名・インストール先変更に依存しない。
- 上記ルート配下を `database/workspace.sqlite`、`attachments/`、`drafts/`、`logs/app.log`、`session/`、`backups/` に分離する。バックアップ対象はDB・管理画像・復旧下書き、ログとChromiumキャッシュは対象外。外部資料原本は対象外。
- 起動テストは明示的な `EW_TEST_DATA_DIR` を必須とし、test-artifacts内の一時フォルダだけを使う。正常終了・再起動しても通常の開発／製品領域へ接続しない。
- Phase 1でDBアダプターと連番Migrationを `src/main/db/` に追加する。`PRAGMA user_version` で版管理、Migration単位のトランザクション、外部キー有効化、SQLパラメータ束縛を必須とする。未知の新しい版／破損／Migration失敗は起動を止め、既存DBを空DBへ置き換えない。変更前バックアップと失敗時の復旧をテストする。Phase 0で空の業務スキーマは先行作成しない。
- ログは起動・終了・preload失敗・renderer異常終了・起動失敗をISO時刻付きで追記。本文や外部資料パスは記録しない。ローテーションと保存処理の障害通知は永続化段階で追加する。

## 技術的な上限と性能基準（設計値、未測定）

上限はライブラリの保証値ではなく、入力保護とメモリ使用量のための本アプリの設計判断。機能・状態・必須プロパティは変更しない。超過時は入力を切り捨てず、理由を示して再編集可能にする。

- サマリはUnicodeコードポイント500文字まで。短文用途と一覧での編集を維持し、一覧表示だけ省略して全文編集可能にする。実装はPhase 1。
- 本文への取り込みはPNG/JPEG、1画像20MiB・展開後2400万画素まで。nativeImageが公式に扱う形式に限定し、管理保存はPNGでメタデータ依存を減らす。アニメーション・SVG・外部URL画像は取り込まない。拡張子だけで判定せずデコードで検証し、原本を変更しない。画像保存と本文参照の確定はPhase 4。
- 報告PNGは1辺8192px・合計3200万画素まで。RGBA画素だけで約122MiBとなるため、この範囲で開始する。超過時は期間・行数・解像度の調整を促し、行を黙って落とさない。実装とメモリ評価はPhase 6。
- 検索の想定データはテーマ100・検討項目10,000（本文平均2,000文字）・資料5,000。検証PCはWindows x64 10.0.26300 / Ryzen 5 5600X / RAM 32GiB / Node 24.22.1。将来の性能試験でデータ生成seed・格納ディスク・照合条件を記録する。
- Phase 4の検索目標は、ウォーム状態で50クエリを実行し、検索API往復のp95 200ms以内（入力debounce 150msを除外）。先頭50結果の表示完了は問い合わせ開始後500ms以内。測定はローカルデータのみ、外部原本へのアクセスなし。現在は検索未実装で、目標値を達成したという記録ではない。

## 2026-11-03 — Phase 1の実装判断

### UIの品質方針

ユーザーの追加指示を製品仕様7章へ反映。市販アプリ並みの完成度を目指し、Notionを参考に、暖色寄りのニュートラル色・細い区切り線・余白と文字の強弱・小さな線画アイコンを用いた。ブランド・ナビ・状態・作成・関連・保存表示をそろえ、標準HTMLの入力とキーボード操作を保つ。アイコンはこのプロジェクト用のSVGを新規作成し、アイコン専用依存を増やしていない。既存のライブラリ版はPhase 0から変更なし。

ホームは表と独立したいつか欄。ページ詳細は頻用資料を本文より上、関連項目と気づき作成を本文の近くに配置。空の日付欄は追加操作で展開する。新規作成は小さなモーダルで、タイトル／テーマ名へフォーカスし、作成途中で閉じても下書きを残す。下書きの破棄は確認してから実行する。明暗両テーマと1366×768の実Electron画像で確認し、文字サイズと薄すぎる文字色を調整した。高DPI・IME実入力・すべての画面サイズの受入は別途行う。

### 永続化・Migration

- `src/main/db/migrations.ts` の連番SQLと `PRAGMA user_version` を使用。[SQLite user_version](https://www.sqlite.org/pragma.html#pragma_user_version)、[トランザクション](https://www.sqlite.org/lang_transaction.html) を確認。Migrationは `BEGIN IMMEDIATE` とCOMMIT、失敗はROLLBACK。将来版のDBと破損DBを拒否し、空DBで置き換えない。既存DBの版を上げる前は [VACUUM INTO](https://www.sqlite.org/lang_vacuum.html) で整合したDBスナップショットを作る。
- 初期スキーマはthemes/items/item_links/applied_edits。テーマ所属はnullableの単一外部キー。状態は6種類のCHECK、関連は方向を保持して逆引きし、同一ペアの重複を防ぐ。外部キー有効、WALとsynchronous=FULL、busy_timeout=1500msで開始する。各値はSQLパラメータで束縛する。UI以外の入力もmainで実行時検証する。
- APIは用途別のメソッドのみ。成功値またはINVALID_INPUT/CONFLICT/NOT_FOUND/STORAGE_FAILEDを返す。rendererからSQL・ファイルパス・任意チャンネルを渡せない。getWorkspace、下書き退避／確定／破棄、関連追加／解除、手動バックアップ、終了時ハンドシェイクを追加した。
- Phase 1の本文はプレーンテキストで永続化し、Enterを改行として保持する。Phase 4で既存文字列を失わないMigrationを用意してTiptapの構造化JSONへ進める。装飾・画像は未実装であり、プレーンテキスト保存を完成した本文機能とは扱わない。

### 編集バッファと復旧

- rendererの `EditorStore` はページ／テーマごとの編集バッファを持ち、[useSyncExternalStore](https://react.dev/reference/react/useSyncExternalStore) で購読する。画面のアンマウントでバッファと保存キューを破棄しない。
- 各変更をmainへ順序付きで退避する。復旧下書きは `drafts/{kind}-{UUID}.json`。一時ファイルをflushしてrenameした後にのみ退避成功を返す。[Node fs](https://nodejs.org/download/release/latest-v24.x/docs/api/fs.html) のwriteFileSync/flushとrenameを使用。タイトル空欄・500文字を超えたサマリも下書きには保持し、DB確定時に検証する。黙って切り捨てない。
- DB自動保存の待機は450ms。これはまとめて書くための待機時間で、復旧下書きの送信は待機しない。IME変換中は下書きだけを退避し、DB確定を止める。作成EnterはisComposingおよびkeyCode=229を拒否する。
- 保存は対象ごとに直列化する。リビジョンによる楽観ロックと編集トークンを使い、古い成功／失敗応答で新しい入力を上書きしない。途中で新しい入力があれば、新リビジョンでその入力を再退避して保存する。失敗時は入力と下書きを保持し、明示的に再試行する。
- applied_editsで保存トークンを記録し、応答が失われた場合の再試行を冪等にする。DB確定後の下書き掃除失敗を保存失敗にはしない。再起動時は確定済みトークンの下書きを除外し、未確定だけを復旧候補として示す。競合を検出した場合は下書きを保持し、ユーザーが現在の入力での置換を確認した場合だけリビジョンを更新して保存する。
- 派生作成時は元ページの未保存変更を先に確定し、mainが元ページからテーマを取得して、いつか状態と派生リンクを一つのトランザクションで保存する。未保存のテーマ変更を取りこぼさない。
- 通常のウィンドウ終了はmainが止め、rendererのflush完了を待つ。DB失敗時は戻る／再試行、下書き退避済みなら下書きを残して終了を提示する。下書き退避も失敗している場合は安全に終了したと扱わない。終了要求応答の待機は10秒で打ち切り、入力を守るため画面へ戻す選択肢を提示する。SIGKILL・端末の強制停止・OS強制終了では、mainが退避成功を返した下書きまでが復旧対象となる。

### 手動バックアップの基盤

設定からアプリ専用backups領域へ作成。サービスの直列キュー内で [node:sqlite backup](https://nodejs.org/download/release/latest-v24.x/docs/api/sqlite.html) によるDBスナップショットを取得し、管理添付・復旧下書きとSHA-256 manifestを一つの世代へ収める。DBのintegrity_check後に `.partial` から完成世代へrenameする。外部原本・セッション・ログはコピーしない。シンボリックリンク／junctionを辿らない。失敗中の世代は.partialのままで、前の完成世代を変更しない。

復元UI・自動バックアップ・世代整理・任意のバックアップ先・ロールバックはPhase 6。今回の検証はテスト世代のDBを別接続で開いて内容を照合し、添付／下書きとmanifestのハッシュを確認した範囲で、A21の完全な復元受入ではない。

### テストと配布の分離

DB・状態・境界・保存キューのテストはNode標準test。実Electronの操作検証は `tests/electron-scenarios.ts` を別のテスト用CJSへビルドし、一時専用領域の4プロセスで作成→再起動→異常終了→復旧を確認する。操作テストのサンプル・固定日付はテストコードだけに置く。配布ASARはmain/preloadの2ファイルとrendererだけを対象にし、テスト用CJS・試作・DB・実行証跡を収容しない。画面キャプチャのGPU依存エラーを避けるため `--smoke-test` の時だけソフトウェア描画に固定する。通常起動のGPU設定は変更しない。

### ユーザー指示による表示・連続作成の調整

ホームの見出しはHOMEへ変更。ホーム／設定の標語、いつか欄の装飾的なキャプション、作成モーダルや気づきボタンの補足を削除し、入力名・保存状態・確認と失敗に必要な説明を残す。2026-11-04の追加指示により、ページ・気づき・テーマの作成成功時は作成モーダルを閉じ、元の一覧・ページを表示する。詳細への自動遷移と空のモーダルの維持は行わない。作成失敗時はモーダルと入力を保持して再試行可能にする。空欄のEnterでは作成処理を開始しない。

## 2026-11-05 — 保存範囲・状態表示・詳細操作を統一

資料の共通情報も用途メモと同様に、資料ID／関連先をキーにしたDocumentEditorPoolで保持する。従来の単一編集バッファと全件flushでは、資料Aの保存失敗が資料Bの詳細表示・終了・原本起動まで妨げていた。詳細の閉じる／ページ移動／再試行はその資料だけ、原本起動はその資料の共通情報だけ、関連解除はその関連先、並べ替えはその文脈をflushする。アーカイブは対象ページ／テーマに関係するメモを対象とし、アプリ終了・バックアップは従来どおり全体の入力保護を確認する。DBスキーマ・保存場所・依存バージョンは変更しない。

資料詳細の通常操作は「閉じる」に一本化し、保存失敗時だけ「再試行」を置く。再試行は詳細を開いたまま保存し、閉じる／関連ページ移動は保存を試みた後に入力バッファを残して移動する。失敗した資料は共通の警告と資料一覧の入力確認導線から再度開ける。下書き退避そのものが失敗した場合もメモリー内の入力は残し、終了時は安全に退出できると扱わない。

保存ラベルとアイコンはshared/save-statusの同じ判定で決め、失敗を進行中より優先する。資料の共通情報・用途メモと、資料一覧の表示条件も上部状態へ含める。詳細内はその資料の状態だけを示す。保護された未確定入力は「下書きを保持しています」であり、「保存済み」と表示しない。

終了応答の型付きAPIへ、検証済みのreason（operation／registration）を追加。空の追加ウィンドウは終了を止めず、未登録の参照先・一括登録の失敗行は登録前入力として扱う。処理中は完了待ち案内、未登録入力は戻る／破棄して終了の確認をmainが表示する。未登録入力の破棄によって別の保存失敗を迂回しないよう、登録前確認の前に実データ・表示設定を全体flushする。登録前参照先は登録用の一時入力で、自動復旧下書きの対象には追加しない。

新しいライブラリや技術上限値の選定はない。既存のElectron IPC・下書きステージング・CAS更新・自動保存間隔を利用する。テスト専用のSQLiteトリガーで資料Aの共通情報／用途メモだけを失敗させ、Bの保存・A再表示と再試行を確認する。終了案内はネイティブダイアログの選択をテスト内で差し替え、実IPCとflush判定を通す。実際のネイティブ画面で全選択肢を操作した確認とは区別する。

### 画像保存とAPI境界

images APIは貼り付けのバイト列、mainのファイル選択、許可リンクの外部起動だけを受ける。mainがUUIDを発行し、attachments/<UUID>.png.pendingをflushしてから.pngへrenameする。成功後にrendererが本文参照を追加する。元画像へは書き込まない。表示URLはworkspace-image://managed/<UUID>.pngで、ハンドラーは正規形の管理ID・通常ファイル・サイズを検証する。パスや任意ファイル読み取りのAPIは公開せず、CSPのimg-srcにこの専用スキームだけを追加する。DB保存時にも参照する管理画像の実在を確認する。

本文からの画像削除は参照だけを除き、画像ファイルをすぐに物理削除しない。下書き・復旧・既存バックアップに必要な画像を保持する。バックアップの既存attachments同梱を利用し、ハッシュ付きmanifestで確認する。未参照画像の回収・バックアップ復元のUIは後続Phaseの対象。

ローカルのスナップショット作成を既存serviceキューへ置き、外部保存先へのコピー／列挙・ハッシュ検証はfs/promisesでキューの外へ分離する。ネットワークコピー待ちでローカル編集要求を同じキューへ詰まらせない。外部コピーは.partialへ書き、検証成功後に完成名へrenameする。完成後にだけ厳格な世代名と検証済み内容の古い世代を30件へ整理する。ローカルの安全コピーも30世代へ整理する。終了時はrendererの全編集・画像・下書きflush後にバックアップを最大6秒待ち、失敗時はmainでローカル保存済みの案内と画面へ戻る／バックアップせず終了を表示する。実UNCの無応答は別途手動未確認。

復元は全入力の退避と確認後、mainで現在データのローカルバックアップを作り、世代を専用restore-pendingへコピー・再検証してreadyをflushする。復元準備中の新規IPCを拒否し、serviceを閉じて[app.relaunch](https://www.electronjs.org/docs/latest/api/app#apprelaunchoptions)／exitする。次回起動でSQLiteを開く前に再検証し、installジャーナルをflushしてdatabase／attachments／draftsのディレクトリ単位で置換する。途中失敗やinstallジャーナルが残る起動ではoldから巻き戻す。成功時はbefore-restore-*に置換前の一式を保持する。巻き戻しが失敗すれば起動を止め、元データを消して空DBを生成しない。これはプロセス中断を想定した回復で、物理ディスク故障の保証ではない。ログ・セッション・バックアップ先設定は復元しない。
